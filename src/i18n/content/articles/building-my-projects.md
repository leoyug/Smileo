---
title: "Practices that help me build projects"
description: "Reminders for moving projects forward: record ideas, start early, finish a version and let someone else try it."
---
Ideas for other things often arrive while I am seriously working on something. Sit down specifically to think of my next project, though, and my mind tends to go blank. To stay focused, I used to put those thoughts aside and plan to return once the current work was done.

Then I could not remember them.

I have been wanting to write that down along with a few other thoughts as reminders for my own projects. I am mainly thinking about small projects I can start myself, from the first idea through making something and showing it to others. There are a few places along that path where I want to work differently.

## Record ideas when they appear

Ideas that interrupt work are often connected to a specific situation. A repeated step is annoying, switching between places is cumbersome, or an existing tool takes a roundabout path through a problem that should be solvable. At that moment, I know what I am doing and what is awkward, so the ideas that follow tend to be grounded.

Those conditions are absent when I set out to hunt for project ideas. It is easy to start with an attractive-sounding feature and work backward to invent reasons to use it. The concept grows richer while the question of when I would actually need it becomes harder to answer.

I want to break the habit of recording it later. When an idea arrives, I should at least note what I was doing and what did not work smoothly, along with any possible solution. A batch file tool is vague. Having to rename exported images by the same rules every time tells my future self why I wanted to build it.

If the thought is already developing, I can write a little more. A title alone is often all that remains when I return, while the specific reasoning that made the idea promising has disappeared. If I have reached that point, I want to preserve more of it.

Of course, following every inspiration immediately can pull me completely away from the work in front of me. I want to retain the reasoning before it fades, then return to the original task. Whether it deserves a project can wait. It is fine to lose interest later; at least I no longer need to keep worrying that I will forget.

## Start before thinking through everything else

An idea creates more questions. Which cases should it support? How should the interface work? Could other people eventually use it? Each question seems worth exploring, and the project gradually becomes something requiring a long preparation phase.

I want to find one part I can act on first.

For the hypothetical image-renaming tool, I could choose a group of files, write down the desired naming rule and run it once. A rough interface is enough if I can see the original names, expected names and actual results. That already gives me something concrete to discuss.

Only then do some overlooked problems emerge. What if names collide? Should useful information in existing filenames be preserved? A rule that felt natural in my head might make no sense with real files. Sitting and thinking makes these things easy to miss.

Starting also helps locate the difficulty. A project I thought I could not build may have only one unfamiliar step, with the rest already manageable. What to learn next becomes much more specific.

For me, starting means a small experiment with a visible result. Spreading out the entire project and making many mutually dependent pieces without one complete operation leaves me unsure what to change next. I want something usable early, even if it does very little.

## Finishing matters more than perfecting

There is almost always one more improvement to make: another feature, a typography adjustment, an interaction that feels slightly off. Personal projects make this especially risky because nobody else sets a deadline. I decide what finished means.

That can be dangerous.

Before beginning a version, I want to write down where I can stop. The renaming tool's first version might support one naming rule, preview the result, warn about collisions and report which files were renamed successfully. Once that works, someone can try it. Other naming rules can wait for the next version.

If each new idea immediately becomes another requirement for this version, the finish line keeps moving. Worse, the more I build, the less willing I become to share it: there is always one last detail, and that detail keeps growing another.

I do not want finishing over perfecting to excuse obvious failures, though. A tool can support a single naming rule, but it must not lose files or report success after failing. I need to distinguish what this version can omit from what it has already promised to do well.

I am willing to accept completion at a smaller scope. A version that works from beginning to end provides a basis for comparison. Later improvements can address specific problems instead of pushing indefinitely against an unfinished project.

## Get outside my own world

When I conceive, build and test a project myself, many things become suspiciously smooth. I know where every button is and which order to follow. I also naturally avoid unfinished areas. A first-time visitor has none of that preparation.

I want to show working pieces to others sooner. It might be an operation demonstration or a usable version. I can explain what it currently does, then find someone with a similar problem and observe how they use it.

In particular, I want to explain less on the project's behalf. Someone testing a renaming tool could use their own files while I watch where they start and where they pause. I will probably want to jump in with instructions, but the hesitation itself is worth preserving. Something I thought was clear may not have been noticed at all.

Asking what do you think rarely tells me what to do next. More than a polite compliment, I want to know whether this is a real problem for them, how they would handle it without the tool, and whether anything still needs doing afterward.

Other people's suggestions do not all need accepting. A sensible feature may serve a different way of working and add more cases to support. I can record it before deciding whether the project should go in that direction.

Showing someone also has a direct effect on me: I have to explain what actually works now. Things still in my head can no longer count toward progress, even if they already feel nearly finished when I think about them alone.

Next time, I hope to say less about what will come later and hand over the current version for one complete use. Afterward, I will probably understand the next changes better than I do now.
